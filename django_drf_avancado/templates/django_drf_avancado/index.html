🌐 Django + DRF Avançado

ORM avançado, serializers e permissions customizadas, signals e middleware — tudo com dados reais no banco. O código de verdade está em:

django_drf_avancado/exemplos.py
django_drf_avancado/serializers.py
django_drf_avancado/permissions.py
django_drf_avancado/signals.py
django_drf_avancado/middleware.py

Pré-requisito: rodar python manage.py popular_dados antes de testar as demos.

1. O problema N+1

Sem otimização, buscar N livros e acessar o autor de cada um dispara 1 query pros livros + N queries, uma por autor. CaptureQueriesContext prova isso contando queries reais.

Ver: demo_problema_n_mais_1()

2. select_related — JOIN no SQL

Traz o relacionamento "para um" (ForeignKey) junto na mesma query, via JOIN. Resolve o N+1 quando o relacionamento é direto.

Ver: demo_solucao_select_related()

3. prefetch_related — para relacionamentos "para muitos"

Faz uma segunda query separada buscando todos os relacionados de uma vez, e junta em memória (Python). É a escolha certa pra relacionamentos reversos ou muitos-pra-muitos.

Ver: demo_prefetch_related()

4. transaction.atomic — tudo ou nada

Garante que todas as operações dentro do bloco acontecem, ou nenhuma acontece (rollback automático em caso de erro).

Ver: demo_transaction_atomic()

5. Serializers customizados

Nested serializers (aninhar um relacionamento no JSON), SerializerMethodField (campo calculado), e a diferença entre validate_<campo> (validação de campo único) e validate() (validação cruzada entre campos).

Ver: AutorSerializer, LivroSerializer

6. Permissions customizadas

A diferença entre has_permission (nível de view, roda antes de saber qual objeto) e has_object_permission (nível de objeto, roda depois de já ter o registro em mãos).

Ver: ApenasLeituraOuAutenticado, ApenasDonoOuLeitura

7. Signals

post_save e pre_delete permitem reagir a eventos do ORM sem acoplar essa lógica dentro do save() do model. Precisam ser importados no ready() do apps.py pra serem registrados.

Ver: signals.py

8. Middleware customizado

Código que roda em toda requisição, antes da view processar e depois dela responder. A ordem da lista MIDDLEWARE define a ordem de execução na entrada (de cima pra baixo) e o inverso na saída.

Ver: TempoDeRespostaMiddleware, LogRequisicaoMiddleware
