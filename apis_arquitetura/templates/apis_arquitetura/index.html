1. Status codes e idempotência

O status code é parte do contrato: 201 criou (com o header Location), 204 deu certo sem corpo, 400 dado malformado, 404 não existe, 409 conflito com o estado atual. Uma operação é idempotente quando repetir deixa o servidor no mesmo estado que uma execução só: GET, PUT e DELETE são, POST não é. Idempotência fala do estado do servidor, não do status code: o segundo DELETE devolve 404 e continua idempotente. Para tornar um POST seguro contra repetição (timeout, clique duplo), o cliente manda o header Idempotency-Key e o servidor devolve a resposta original em vez de criar de novo. Mesma chave com corpo diferente dá 409.

Ver: LivroListaView, LivroDetalheView em views.py

2. Versionamento de API

Serve para mudar a API sem quebrar quem já a usa. Adicionar campo ou endpoint não quebra clientes; remover, renomear ou mudar o tipo de um campo quebra, e pede versão nova. Três estratégias: na URL (/v2/, a mais comum e fácil de operar), em header (URL limpa, mas difícil de testar) e query param (simples, porém ambíguo). O ciclo de vida de uma versão: lançar a nova, anunciar a depreciação da antiga (headers Deprecation e Sunset), manter as duas por uma janela, monitorar quem ainda chama a antiga e só então remover.

Ver: LivroVersionadoView, LivroV2Serializer

3. Autenticação: sessions, JWT e OAuth2

Session é stateful: o servidor guarda a sessão e o cliente só leva o ID num cookie. É fácil de revogar e é o que o Django Admin usa. JWT é stateless: o próprio token carrega as informações, assinadas. Qualquer servidor valida só com a chave, mas não há como revogar antes do exp sem uma blacklist, que tira o caráter stateless. O token são três partes (cabeçalho, carga e assinatura): a carga é só base64, legível por qualquer um, então nunca leva segredo. A assinatura garante integridade, não sigilo. Um access curto (5 min) trafega em toda requisição, e um refresh longo só serve para pedir um access novo. OAuth2 não é um jeito de fazer login: é um protocolo de autorização delegada ("este app pode acessar meus dados no serviço Y sem minha senha"). A identidade vem de uma camada em cima, o OpenID Connect. Por fim, 401 é "não sei quem você é" e 403 é "sei quem você é, mas você não pode".

Ver: PerfilView, SomenteAdminView, exemplos.py (demo_anatomia_do_jwt, demo_adulterar_jwt, demo_expiracao)

4. Swagger / OpenAPI real

O drf-spectacular gera o schema OpenAPI, o padrão de mercado que qualquer ferramenta entende, e o Swagger UI desenha a interface a partir dele. Difere da Browsable API nativa do DRF, que é navegável mas específica do framework e vive na própria URL do endpoint. O @extend_schema descreve respostas e parâmetros que o drf-spectacular não consegue inferir (como o header Idempotency-Key), e o type hint de retorno em um SerializerMethodField é o que permite descrever o campo sem warning. É o equivalente ao /docs que o FastAPI traz de fábrica.

Ver: /schema/swagger-ui/, @extend_schema em views.py

5. Service layer e repository pattern

Separa a view em três camadas. A view traduz HTTP (lê a requisição, chama o service, converte erros em status code). O service guarda as regras de negócio e não importa nada de Django. O repository concentra as queries. O service recebe os repositórios no construtor (injeção de dependência), então nos testes entra um repositório falso em memória, e as regras são testadas sem banco e sem HTTP. Os erros de domínio dizem o que deu errado em termos de negócio, e a view decide o status: 400 é formato inválido (quem decide é o serializer) e 422 é dado bem formado que viola uma regra (quem decide é o service). O custo é mais arquivos e indireção. Em Django o ORM já faz papel de repositório, então em CRUD simples isso é cerimônia. Compensa quando há regra de negócio relevante ou quando a mesma regra é chamada de lugares diferentes (view, task do Celery, comando).

Ver: services.py, repositories.py, LivroCamadasView, test_service_layer.py

6. Monolito vs microsserviços

MonolitoMicrosserviços
DeployUma unidade sóCada serviço sozinho
Chamada entre partesFunção local: rápida e confiávelRede: latência, timeout, falha parcial
TransaçõesACID de verdadeConsistência eventual (saga)
EscalaTudo juntoSó o serviço que precisa
FalhaPode derrubar tudoIsolada, se bem projetada
Complexidade operacionalBaixaAlta (observabilidade, contratos, deploys)

Microsserviços não são "o monolito melhor": trocam um problema por outro. O caminho comum é começar com um monolito modular e extrair um serviço quando a dor é real (um módulo que precisa escalar diferente, uma equipe que precisa de autonomia). O anti-padrão clássico é o monolito distribuído: serviços separados que continuam acoplados e precisam ser implantados juntos, com a complexidade de rede e sem nenhum ganho. Cada serviço deve ser dono dos seus dados, e a comunicação pode ser síncrona (HTTP, gRPC) ou assíncrona (filas, eventos, como o Celery).

Neste projeto: o EstudosPythonPleno é um monolito modular, o worker do Celery é o mesmo código em outro processo, e o EstudosFastAPI é um serviço separado. Ao virar serviços, o Idempotency-Key, o versionamento e o JWT deixam de ser detalhes e passam a ser requisitos.
