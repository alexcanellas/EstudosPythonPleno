1. SQL puro (via cursor) vs ORM

O ORM sempre vira SQL por baixo dos panos. connection.cursor() dá acesso direto ao banco, sem passar pelo ORM — útil pra entender o que o ORM está de fato gerando, ou pra query complexa demais pro ORM expressar bem.

Ver: demo_sql_puro_vs_orm()

2. EXPLAIN QUERY PLAN

Pede pro banco explicar a estratégia de execução de uma query, sem rodar ela de verdade. SCAN = varredura completa da tabela (lento); SEARCH = usou um índice pra pular direto pro dado (rápido). É a ferramenta #1 pra descobrir por que uma query está lenta.

Ver: demo_explain_query_plan()

3. Índices — ganho de performance real

Um índice é uma estrutura auxiliar (B-Tree) que o banco mantém ordenada, permitindo pular direto pro dado. Tem custo: toda escrita (INSERT/UPDATE/DELETE) fica um pouco mais lenta, porque o índice também precisa ser atualizado. A demo cria 50 mil registros temporários pra medir o ganho de verdade, e limpa tudo no final.

Ver: demo_indice_performance()

4. Isolamento de transações e select_for_update

Race condition: duas transações lendo o mesmo dado ao mesmo tempo, cada uma aplicando uma mudança sem saber da outra — uma pode sobrescrever a mudança da outra. select_for_update() resolve isso travando a linha no banco até a transação terminar.

Ver: demo_race_condition_sem_protecao(), demo_select_for_update()

5. Migration manual

Diferente de uma migration gerada automaticamente pelo makemigrations, essa foi criada com --empty e escrita na mão, adicionando um índice permanente no campo titulo — a mesma mudança que fizemos manualmente com SQL puro na demo de índices, agora versionada e reprodutível via Meta.indexes no model.

Ver: django_drf_avancado/migrations/0002_adicionar_indice_titulo.py
