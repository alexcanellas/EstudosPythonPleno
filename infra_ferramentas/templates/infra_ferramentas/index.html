1. Variáveis de ambiente e segredos

Configuração que muda entre ambientes e segredos ficam fora do código, no .env (nunca versionado). O .env.example documenta quais variáveis o projeto precisa, sem os valores reais. O python-decouple lê essas variáveis já convertidas pro tipo certo (cast=bool, cast=Csv()) — sem isso, bool("False") daria True, porque toda string não vazia é truthy. Uma variável obrigatória sem default falha cedo e alto, em vez de silenciosamente virar None lá na frente.

Ver: demo_leitura_com_tipos(), demo_ordem_de_prioridade(), demo_variavel_obrigatoria_ausente(), demo_mascarar_segredo()

2. Cache

Cache-aside: pergunta ao cache primeiro; se não achar (miss), busca na fonte e guarda o resultado pro próximo. O ganho de performance é real e mensurável — nas demos, a primeira busca leva ~1s (foi na fonte) e as seguintes são quase instantâneas (vieram do cache). O lado difícil é a invalidação: se a fonte muda e ninguém avisa o cache, ele serve dado desatualizado até expirar pelo TTL. O backend é trocável só mudando o CACHE_URL no .env — em memória (LocMemCache) para desenvolvimento simples, Redis quando rodando via Docker.

Ver: demo_operacoes_basicas(), demo_cache_aside(), demo_invalidacao(), demo_ttl()

3. Git

merge preserva o histórico como aconteceu, com um commit de merge juntando as duas linhas. rebase reescreve os commits da branch por cima da base, deixando o histórico linear — mas gera hashes novos, por isso nunca se faz rebase de uma branch que outras pessoas já baixaram. Conflito acontece quando as duas branches alteram a mesma linha: o Git para no meio e marca o arquivo com <<<<<<< HEAD / ======= / >>>>>>>, esperando a resolução manual.

Ver: demo_merge_vs_rebase(), demo_criar_conflito()

4. CI/CD

CI roda os testes automaticamente a cada push ou Pull Request, numa máquina virtual limpa — prova que o código funciona fora da sua máquina, sem depender de nada que só exista localmente. CD é a continuação natural: publicar o que passou no CI. O workflow (ci.yml) é só YAML versionado junto do código: baixa o repositório, configura o Python, instala as dependências do requirements.txt e roda pytest + coverage.

Ver: .github/workflows/ci.yml

5. Docker

O Dockerfile descreve como construir uma imagem: uma "receita" de sistema de arquivos congelado. Multi-stage build separa onde as dependências são instaladas (builder) do que realmente roda em produção (final) — só o necessário é copiado entre os estágios, deixando a imagem final menor. Rodar como usuário não-root é prática de segurança comum, mas exige chown explícito na pasta da aplicação, senão o processo não tem permissão de escrita nela. O docker-compose.yml sobe vários serviços relacionados juntos (aqui, Django + Redis), conectados numa rede interna onde cada serviço enxerga o outro pelo nome.

Ver: Dockerfile, docker-compose.yml, .dockerignore

6. Celery + Redis

Resolve um problema específico: tarefa demorada (e-mail, relatório, chamada de API externa) não pode travar a requisição HTTP. A view chama .delay(), que só enfileira a tarefa no Redis (instantâneo) e devolve resposta na hora. Um processo separado, o worker, fica de olho na fila e executa o trabalho pesado em paralelo, sem o usuário esperar.

Os 3 papéis:

  • Django (view) — enfileira com .delay(...), segue na hora
  • Redis (broker) — só guarda a fila de "bilhetes", não executa nada
  • Worker — processo rodando continuamente, consome a fila e executa de verdade

Quando usar: a operação não precisa de resposta imediata pro usuário ver o resultado (e-mail, notificação), é pesada o bastante pra impactar a experiência (mais de ~1s), ou precisa de retry automático em caso de falha.

Quando NÃO usar: a operação é rápida o suficiente pra rodar na própria requisição, ou o resultado precisa aparecer imediatamente na mesma tela (ex: total de um carrinho).

Celery vs asyncio — os dois resolvem espera, mas em escalas diferentes: asyncio é pra esperar I/O sem travar dentro da mesma requisição (ex: 3 chamadas de API em paralelo, antes de responder); Celery é pra trabalho que continua rodando depois da requisição já ter terminado, num processo totalmente separado.

Ver: tasks.py, demo_celery_basico(), demo_celery_multiplas_tarefas_em_paralelo(), demo_celery_com_falha()
